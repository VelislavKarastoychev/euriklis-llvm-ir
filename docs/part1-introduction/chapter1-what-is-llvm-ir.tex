\chapter{What is LLVM IR and Why Is It Useful?}

\section{The Compiler Problem}
Traditional compilers are monolithic: each language needs its own complete toolchain targeting every architecture. If you have \(M\) languages and \(N\) architectures, you need \(M \times N\) implementations. This becomes unsustainable as both language diversity and hardware complexity grow.

LLVM solves this by introducing an \textbf{intermediate representation (IR)}—a stable, language-independent, architecture-independent format that sits between high-level source code and low-level machine code. 
Classical compiler theory suggests that \(M\) languages targeting \(N\) architectures require \(M \times N\) distinct back-ends. In practice, LLVM collapses this to \(M\) front-ends plus lightweight target descriptions, because the bulk of back-end logic (instruction selection, scheduling, register allocation, code emission) is shared within LLVM itself. You parameterize the backend with a data layout specification, calling convention, and a modest set of target-specific hooks rather than re-implementing a complete code generator for each architecture. This reduces compilation process complexity from \(M \times N\) to \(M + N\).

\section{What is LLVM IR?}
The acronym LLVM stands for \textbf{\textit{"Low Level Virtual Machine"}}. It began as an open-source compiler infrastructure project at the University of Illinois in 2000, originally designed to provide a modern, SSA-based compilation technique for arbitrary static and dynamic programming languages.

The design and core concepts developed in the LLVM research project have proven highly advantageous for language implementation and compilation due to its unified instruction set architecture (ISA) and the \textbf{conceptual similarity} between LLVM IR and real assembly languages. Consequently, the project has evolved into a comprehensive ecosystem of distinct subprojects providing reusable libraries and ISA specifications.

\textbf{The compilation pipeline:} When a new programming language is created, its syntax must first be parsed by a parser that validates code consistency against the language's grammar rules. The parser then constructs a data structure called an \textbf{Abstract Syntax Tree (AST)}, which represents the program's hierarchical structure. The AST nodes must then be translated into human-readable, machine-like instructions. This low-level representation is called \textit{assembly language}.

However, each hardware architecture defines its own \textbf{Instruction Set Architecture (ISA)}, meaning the same AST must be translated into multiple distinct assembly languages—one for each target platform. This architectural diversity significantly complicates the language compilation process.

To address this challenge, LLVM introduced the concept of a \textbf{unified abstract low-level language} with a common ISA that is structurally analogous to native assembly languages. The compilation process (translation to machine code for each architecture) is then executed by the LLVM compiler infrastructure, which acts as a virtual machine for this abstract representation.

LLVM IR is therefore a low-level intermediate language that resembles assembly but with several critical differences:

\begin{itemize}[noitemsep]
  \item \textbf{Strongly typed}: Every value has an explicit type (\texttt{i32}, \texttt{float}, \texttt{ptr}, etc.)
  \item \textbf{Platform-independent}: Same IR works for x86, ARM, GPU, WebAssembly
  \item \textbf{SSA form}: Every variable is assigned exactly once (enables aggressive optimizations)
  \item \textbf{Infinite registers}: Virtual registers with \texttt{\%} prefix (backend maps to physical registers)
  \item \textbf{Explicit control flow}: Basic blocks and explicit branches instead of goto
\end{itemize}

Example LLVM IR function:
\begin{lstlisting}[style=ir]
define i32 @add(i32 %a, i32 %b) {
entry:
  %result = add i32 %a, %b
  ret i32 %result
}
\end{lstlisting}

This is:
\begin{itemize}[noitemsep]
  \item Human-readable (unlike binary machine code)
  \item Optimizable (unlike high-level source code)
  \item Portable (unlike assembly language)
\end{itemize}

\section{Static Single Assignment (SSA) Form}

SSA is a property where each variable is assigned exactly once and every use refers to a specific definition. This makes data flow explicit and enables powerful optimizations.

\textbf{Non-SSA code:}
\begin{lstlisting}[style=ir]
x = 1
x = x + 2  // x is assigned twice (not SSA)
\end{lstlisting}

\textbf{SSA code:}
\begin{lstlisting}[style=ir]
%x1 = 1
%x2 = add i32 %x1, 2  // Each value has unique name
\end{lstlisting}

Benefits:
\begin{itemize}[noitemsep]
  \item Constant propagation: \texttt{\%x2} is provably 3
  \item Dead code elimination: Unused definitions can be safely removed
  \item Register allocation: Clear lifetime of each value
\end{itemize}

\section{Basic Blocks and Control Flow}

LLVM organizes code into \textbf{basic blocks}—straight-line sequences of instructions with no branches except at the end:

\begin{lstlisting}[style=ir]
define i32 @max(i32 %a, i32 %b) {
entry:
  %cmp = icmp sgt i32 %a, %b  // Compare: a > b?
  br i1 %cmp, label %if.then, label %if.else

if.then:
  ret i32 %a

if.else:
  ret i32 %b
}
\end{lstlisting}

Each basic block:
\begin{enumerate}[noitemsep]
  \item Has a unique label (\texttt{entry}, \texttt{if.then}, \texttt{if.else})
  \item Contains sequential instructions (no control flow in the middle)
  \item Ends with a \textbf{terminator} (\texttt{ret}, \texttt{br}, \texttt{switch})
\end{enumerate}

\section{The PHI Instruction}

When control flow merges, SSA form requires a special instruction to select the correct value:

\begin{lstlisting}[style=ir]
define i32 @abs(i32 %x) {
entry:
  %is_neg = icmp slt i32 %x, 0
  br i1 %is_neg, label %negate, label %done

negate:
  %neg = sub i32 0, %x
  br label %done

done:
  %result = phi i32 [ %x, %entry ], [ %neg, %negate ]
  ret i32 %result
}
\end{lstlisting}

The \texttt{phi} instruction says: "If we came from \texttt{\%entry}, use \texttt{\%x}; if we came from \texttt{\%negate}, use \texttt{\%neg}."

\section{Modules, Functions, and Targets}

LLVM IR is organized hierarchically:
\begin{itemize}[noitemsep]
  \item \textbf{Module}: Top-level container (one per compilation unit)
  \item \textbf{Functions}: Named code units with parameters and return types
  \item \textbf{Basic blocks}: Control flow nodes within functions
  \item \textbf{Instructions}: Individual operations (add, load, store, etc.)
\end{itemize}

Each module specifies its \textbf{target}:
\begin{lstlisting}[style=ir]
target triple = "x86_64-unknown-linux-gnu"
target datalayout = "e-m:e-p270:32:32-i64:64-f80:128-n8:16:32:64-S128"
\end{lstlisting}

The triple format is \texttt{architecture-vendor-os}:
\begin{itemize}[noitemsep]
  \item \texttt{x86\_64-apple-darwin} - macOS on Intel
  \item \texttt{aarch64-unknown-linux-gnu} - Linux on ARM (Apple Silicon, AWS Graviton)
  \item \texttt{nvptx64-nvidia-cuda} - NVIDIA GPUs
  \item \texttt{amdgcn-amd-amdhsa} - AMD GPUs
  \item \texttt{wasm32-unknown-unknown} - WebAssembly
\end{itemize}

\section{Why LLVM IR Is Useful}

\begin{enumerate}[noitemsep]
  \item \textbf{Write once, run anywhere}: Generate IR once, compile to x86, ARM, GPU, WASM
  \item \textbf{Optimization}: LLVM's optimizer works on IR (loop unrolling, vectorization, inlining)
  \item \textbf{Tooling}: IR can be analyzed, transformed, interpreted, or JIT-compiled
  \item \textbf{Incremental compilation}: Modules can be linked together
  \item \textbf{Language experimentation}: Build new languages without writing a full compiler backend
\end{enumerate}
